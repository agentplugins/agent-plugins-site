---
title: Build an Agent Plugin
description: Create the smallest portable package and add components in fixed locations.
---

An Agent Plugin is a self-contained directory. Every plugin has a root `plugin.json`; skills, MCP servers, and hooks are optional.

## Create a minimal plugin

```text
hello-plugin/
├── plugin.json
└── skills/
    └── greet/
        └── SKILL.md
```

Create `plugin.json`:

```json title="plugin.json"
{
  "$schema": "https://agent-plugins.org/schemas/1.1.0/plugin.schema.json",
  "name": "hello-plugin"
}
```

Create the skill:

```markdown title="skills/greet/SKILL.md"
---
name: greet
description: Greet the user and offer help.
---

Greet the user and offer help.
```

A skills-capable client loads `plugin.json`, discovers the immediate children of `skills/`, and validates each `SKILL.md` against the Agent Skills specification. To add MCP servers, place `mcp.json` at the plugin root using the same Agent Plugins schema version.

For a copyable package with a complete manifest and a real skill, see the [Agent Plugins example](https://github.com/agentplugins/agent-plugins-example).

## Describe your plugin

Give the plugin a readable name and explain what it provides by adding `displayName` and `description` to `plugin.json`. For this example, you could use `"displayName": "Hello Plugin"` and `"description": "A friendly greeting skill."`. Other [manifest fields](/plugin-authors/manifest) let you identify releases with `version`, credit an `author`, and provide project links and licensing information.

To include an icon, save a PNG image as `assets/icon.png` in the plugin root. Start with a square 512×512 canvas; use simple shapes and padding, and check that it remains recognizable at about 16×16 pixels on light and dark backgrounds.

You can also provide the same icon in other formats, using lowercase filenames such as `assets/icon.svg` or `assets/icon.webp`. Include PNG for broad support. Clients choose which supported representation to use and whether to display icons.

## Package boundaries

Files supplied by the package must resolve within the plugin root. Configuration fields defined as plugin-relative paths begin with `./`; symlinks and equivalent filesystem mechanisms must not be used to escape the package.
